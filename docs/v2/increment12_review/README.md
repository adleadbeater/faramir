## Migration steps (`scripts/migrate_sheets.py`)

1. **Validate.**
   - `state` must be valid v1 or v2.
   - `suggestions` must be v1, v2 or empty.
   - A v2-named tab with another header is refused.
   - **Nothing is written if validation fails.**
2. **Suggestions to v2.** Ids and delivery columns are appended. The original 17 columns are never written; that covers picks, Slack timestamps, thumbs and thread feedback. The result is read back and verified.
3. **State integrity init.** `state_lkg` (an exact copy) is created and verified, then `state_meta`.
4. **State to 20 columns.** This goes through the normal state protocol: backup, write, read-back checksum, meta confirm.
   - The **exact cell text** is written. The rows are identical, and the three new columns start blank.
   - Editor values come from the live tab.
5. **Create missing tabs, header only:** `Usage`, `identity_overrides`, `weekend_history`, `weekend_collections`. An empty tab left by a crash gets its header written.
6. **Verify the whole workbook** with preflight's checks.
7. **Write the schema marker** `faramir_meta.schema_version=2` last. It is read back.

**Tests** (16) run against a realistic v1 workbook: 6 state rows with an editor override and notes, and 7 suggestion rows covering Slack timestamps, reactions, thread feedback, a duplicated pick, a row without ids and an unposted row. They cover:

- the plan writes nothing;
- the rollback plan;
- three refusal cases with zero writes;
- a full apply that **preserves every state cell and editor value, the 17 suggestion columns byte for byte, and the Usage and corpus_meta tabs**;
- the marker is the last write;
- idempotent re-runs;
- a **crash during the suggestions update, the state write, a new tab's header, or the marker**: in each case preflight still fails, and a re-run completes;
- dry-run records only;
- `--apply` refuses without confirmation, or while `FARAMIR_ENABLED` is unset;
- a migrated workbook passes preflight.

## Weekend-history integrity (requirement 3)

- **The ids are scoped** to source, chart type, reporting weekend and canonical content. Identical figures on two weekends give different `collection_id` and `record_id` values, and the two stay independently readable (tested).
- **Concurrent runs with different versions** (tested):
  - the later *retrieval* wins even when its commit landed first;
  - shuffling the event and history rows changes nothing;
  - retrieval times with different UTC offsets compare correctly;
  - an exact tie is reported, not guessed, and a later retrieval resolves it.

## Deviations from spec P0-7

- **No `runs` tab.** Run records are the uploaded run artifacts (`report.json`, recorded writes, Slack preview), as they have been since Increment 3. S7's "first `runs` row" check becomes "first run artifact and Slack output".
- **The spec's `weekend_snapshots` is `weekend_collections`,** following §5.1.
- **A new variable, `FARAMIR_MIGRATION_ENABLED`, gates `migrate.yml` apply.** Apply also requires `FARAMIR_ENABLED` not 'true', so scheduled runs are off during a migration (PR-17).
